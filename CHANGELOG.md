## [4.9.0] - 2026-10-24

Games go live on Summer's automatic checks, with Summer's review afterwards: `summer_go_live` and `summer_publish_build` read that review, and name the platforms a hosted release left out.

- **`summer_go_live` reads Summer's review of a live game** (the store's `/review` route, which replaces `/approval`).
  - **On hold:** when Summer's staff put a live game on hold and its newest store page is the one they reviewed, it answers `on_hold` with their message: make the changes with `store.update_listing`, then publish the newer page. A new build alone does not lift a hold. A newer draft page is published, which lifts it.
  - **Taken down:** it answers `blocked` with `taken_down`.
  - A sent-back page's decision comes from the review's `latestReview`; while the platform lacks it, from `/approval` when it answers; else the page still reports `needs_changes` and points at `store.status`. On a platform without `/review`, a first-launch hold reports as Summer's, as before. The waiting answer no longer carries `approvalState`.
- **Platforms a hosted release left out: `notIncluded` and `notUsed`.** `summer_go_live` reads `droppedTargets` from the release, answers `notIncluded` (one entry per platform: the reason, `checkErrorCode` and the line to tell the creator, such as "iOS isn't included: this build couldn't be checked for iPhone.") and goes live on the platforms the release kept instead of waiting for the others. `notUsed` names a newer client the release did not use (that platform stays live with its current client). The live answer's `next` names both.
- **`playable_release_required` answers `blocked`** with the platform's own message, or "Upload a build that includes your game's apps so they can be checked against the new server."
- **Setup names an older `summer` on PATH.** After `npx -y summer-engine@latest setup`, a stale global `summer` (3.1.0) first on PATH ran on the next `summer login`. Setup now says which one it is and how to update it (`npm install -g summer-engine@latest`, or `brew upgrade summerengine/tap/summer`), and to use `npx -y summer-engine@latest login` until then; `--json` lists it in `warnings`.
- **"Summer is still checking this; nothing to do on your side."** When a publish's checks have run over an hour, `summer_go_live`'s waiting answer and `summer_publish_build`'s hold say so, with the time (`stillCheckingSince`).
- **`summer_publish_build`'s hold** reads the review too: on hold (with the changes to make), taken down, or Summer's own hold. `approval_denied` now reads "This game was taken down, so it can't take new builds."
- **Copy:** the README, `AGENTS.md`, the project `AGENTS.md` block and the `publish-your-game` skill say a game is live once the automatic checks pass, with staff review afterwards, and tell an automatic-check rejection from a staff hold and a take-down.
- **Windows forms for the release checks.** The `release-readiness`, `multiplayer-publish` and `bounded-engine-runs` skills now give every check a PowerShell form next to the `sh` one: `Expand-Archive` in place of `unzip`, and a small `Run-Summer` helper that bounds a run with `Start-Process` and reads Summer.exe's `--log-file`, in place of `perl` and `grep`.
- The operations catalog is synced from PublicSummerEngine main: the October 2026 models in `assets.generate_image`, `assets.generate_audio`, `assets.generate_sfx_choices` and `assets.generate_video` (among them `nano-banana-2.1`, `flux-3`, `ideogram-4.5`, `recraft-4.1`, `eleven_v4`, `music_v2_5`, `mirelo-sfx-2.0`, `kling-4` and `vidu-q4`), and 480p video. Also Mathias's frontier list (PublicSummerEngine #1418, #1436): the 3D models `hunyuan3d-v3`, `tripo-p1`, `pixal3d`, `trellis-multi`, `hunyuan3d-v2-multiview(-turbo)`, `rodin-2.5` and `tripo-h3.1`; HeyGen video and voices, Qwen3 TTS, Seed Audio 1.0, Gemini 3.1 Flash TTS, MiniMax Speech 2.8 Turbo, Lyria 2 and MiniMax Music; `assets.generate_video` takes `referenceImageUrls` and `videoUrl` for the reference, video-to-video, motion-transfer and add-sound models (`kling-4-ref`, `minimax-h3-max-reframe`, `kling-video-to-audio`, `thinksound`, ...); and `assets.generate_motion` takes `backend: "hunyuan-custom"` with `hunyuanModel` (Hunyuan Motion or Fast).
- **The Summer Board skills ship in the library.** `summer-board` (join, wait, tasks, claims, file handoff, pings, the canvas, and section 7b: one frame per topic, a numbered grid of cards, a summary note with the next step at the top) installs with setup. `summer-board-types`, `summer-board-modeling` and `summer-board-to-game` are in the library (`summer_docs_read`), routed from `summer-board`. Synced from PublicSummerEngine main. To fit the installed-description budget, the `summer-store`, `concept-to-level` and `summer-cli` descriptions are shorter.

## [4.8.0] - 2026-10-24

The Summer API with the Summer sign-in (no static API keys), Studio inside the Summer app, and agents that show the person what they work on. 4.7.0 and the 2026-10-22 4.8.0 draft were never published; this 4.8.0 includes them (sections below).

- **`engine.view_set` (`summer_view_set`) shows the person what the agent works on**: the Summer app's view (home, chat, 3D, 2D, script, game, Studio), the right rail, the focus and the nodes to frame, through the engine's `SetView` operation. Needs Summer Engine 4.6 or newer.
- **`studio.radio`**: agents read and play Summer Radio in the person's open Studio tab (state, play, stop, station, track, next, previous, volume). The operations catalog is synced from PublicSummerEngine main (262 operations).
- **A generated file never saves into Summer's own folders.** `out` on the generate operations, `assets.get` and `jobs.wait` refuses a game's `.summer/local` (checkpoints, project id) and `~/.summer` (sign-in, runtime), with a warning; nothing is downloaded. The game's memory beside it (`.summer/GameSoul.md`, `.summer/memory/`) is unchanged.
- **`projects.open_local` switches the running editor.** When Summer Engine already has another project open, that editor now opens the asked one in the same window (the engine's `SwitchProject` operation) instead of answering "another project is open". The MCP says "Opening <game>…" at once (MCP progress) and waits up to 10 s for the new editor to register, then connects to it. An editor without the operation keeps the old answer and names the open project. Other tools never switch the open project.
- **Signed out? Cloud tools answer with a sign-in link.** When an MCP tool needs the Summer sign-in (`not_signed_in`) or the store approval (`store_login_required`), its answer now ends with a link the agent shows to the person. The MCP starts the same browser sign-in `summer login` uses (`cli_session`) without opening anything, waits for it in the background, and saves the token to `~/.summer`, so the next call works with no restart or reinstall. Engine tools keep working signed out. One link per process until that sign-in finishes or expires (15 minutes).
- **`summer api` and the `summer_api_*` MCP tools use the Summer sign-in on this computer**: the same Supabase OAuth 2.1 login (PKCE, a loopback redirect on 127.0.0.1) as the store tools. It stores the refresh token in `~/.summer/oauth-token` and refreshes by itself. Each app spends the person's paid credits up to the limit they set in Connected apps.
- **`summer api run --batch jobs.jsonl`** queues up to 500 Summer API jobs at once (`POST /v1/batches`), one job per line (`model`, `input`, optional `idempotencyKey`), all or none: when paid credits or the app's limit cannot cover them all, nothing runs and the error says how many fit. `--wait` follows every job, `--download [dir]` saves their files, and the JSON summary prints when piped. The MCP tool `summer_api_batch` does the same. No rate limits on paid usage: jobs past the account's running slots answer `queued` and start in order.
- **`summer api` on Windows.** `--input "@input.json"` reads the input from a file (Windows PowerShell 5 strips the quotes inside `'{"prompt":"..."}'`, and cmd.exe has no single quotes). Batch and input files may be UTF-16 (what Windows PowerShell 5 writes with `>`) or UTF-8 with a BOM, with CRLF lines. Saved files never get a name Windows keeps for a device (`CON`, `NUL`, `COM1`...) or a `:` that would write an NTFS stream. Writing the sign-in to `~/.summer` retries for a moment while antivirus or another Summer process has the file open, and `out` refuses `~/.summer` in any letter case on Windows. CI runs the Summer API and sign-in tests on Windows, macOS and Linux.
- **`summer token`** prints a one-hour access token for curl: `curl -H "Authorization: Bearer $(summer token)" https://www.summerengine.com/v1/models`.
- **Studio page ops run in the Summer app's own Studio tab.** `summer_call` sends `studio.map`, `studio.page`, `studio.use_page`, `studio.read_form` and `studio.submit_form` to the running Summer Engine (`POST /api/studio`) when it lists them in `capabilities.studioPage`, with the same input and answers and no store sign-in. When the app has no Studio tab (`no_tab`) or is not running, they go to Summer's server as before.
- The operations catalog is synced from PublicSummerEngine main: `account.usage` (plan, share used and refill day, in words) and asset generations in `jobs.list`.
- **Studio pages open in the Summer app's Studio tab.** `studio.open` (`summer_open`, `summer open`) with a `/studio...` page sends the running Summer Engine `Navigate {target: "studio", path}` when the engine lists the `studio` destination, so the app's own Studio tab moves instead of a browser opening. With the engine off or an older engine, the browser opens as before.
- **Skills `summer-api` and `summer-router`.** `summer-api`: sign in, models, estimate, one job or a batch, follow and download, money refusals (`no_credits`, `over_limit`), prompts per asset type. `summer-router`: AI characters in games on Summer Games (early preview): client and server calls, the character document, tools, speech and images, caps and error tags. `ai-characters-in-games` is retired (its id points to `summer-router`).
- **`summer router <action>`** runs the Summer Router operations from a shell: `save-character`, `test-character`, `models`, `settings`, `set-settings`, `usage` and the rest. The operations catalog is synced from PublicSummerEngine main.
- `summer_api_run`, `summer_api_batch` and `summer_api_job` name `no_credits` and `over_limit`, and say that Summer API jobs run to the end once accepted.
- **Removed:** `summer login --api-key`, the MCP tool `summer_api_key_login` (operation `account.api_key_login`), `SUMMER_API_KEY` and `~/.summer/api-key`.

## 4.8.0 draft - 2026-10-22 (not published)

The Summer API from a shell and from MCP. 4.7.0 was not published to npm; 4.8.0 is the first release with it (the [4.7.0] section below).

- **`summer api models|estimate|run|jobs`** call the Summer API (`/v1`) with the Summer API key on this computer (`summer login --api-key`, or `SUMMER_API_KEY`). `models` lists the curated game-dev models with their input and USD price (one model by id, `--capability` to filter); `estimate <model> --input '<json>'` prices one exact job and gives a quote id; `run <model> --input '<json>'` spends the person's credits within the key's limit, with one idempotency key per run, `--quote`, `--wait` to follow the job and `--download [dir]` to save its files; `jobs <id>` reads, follows (`--wait`), downloads or `--cancel`s a job. JSON when stdout is not a terminal (or `--json`), a short summary otherwise.
- **MCP tools** `summer_api_models`, `summer_api_estimate`, `summer_api_run` and `summer_api_job` do the same (operations `models.list`, `models.estimate`, `models.run`, `models.job`, local), in the assets and full profiles.
- **Until Summer opens the API**, `summer api` and `summer login --api-key` print one line, "Summer API is not open yet.", and exit 1.
- The operations catalog is synced from PublicSummerEngine main.

## [4.7.0] - 2026-10-22

A Summer API key for your agent with one Allow click, and Node 22.

- **A Summer API key for your agent with one Allow click.** `summer login --api-key` (and the MCP tool `summer_api_key_login`, operation `account.api_key_login`) asks Summer for a key: the person opens the Summer page it names, checks the code matches and presses Allow, choosing the spend limit there. The key is saved to `~/.summer/api-key` (owner-only, like `auth-token`) and is never printed or returned to the agent; `SUMMER_API_KEY` wins over the file. Without a terminal, `summer login --api-key` prints JSON lines (`needs_approval` with `approve_url` and `user_code`, then `approved`, `denied`, `expired` or `failed`). `summer logout` removes the key too. Until Summer turns API keys on, the request answers `keys_unavailable`.
- **Node 22+** (`engines.node >= 22`, was 20). Node 20 reached end of life on 2026-04-30 and gets no security fixes. `summer doctor` now fails on Node below 22, and CI runs the CLI on Node 22.23.4 (the 2026-10-21 security release) on macOS, Windows and Ubuntu.

## [4.6.0] - 2026-10-21

A first game that looks finished, and `summer setup` for the Summer desktop app's one-click agent connect.

- **`summer setup` for installers: find the agents, read each step, run a bundled Node.js.** For the Summer desktop app's installer, which connects the person's coding agent in one click and ships its own Node.js (Claude Code and Codex install without one).
  - **`summer setup --detect --json`** lists every supported agent: whether it is installed (`installed`, `programFound` and each hit in `detectedBy`: a command on PATH or in the usual install folders, a macOS app or Windows program, the agent's own folder, a VS Code extension), its MCP config file, and whether that file already lists `summer-engine`. It writes nothing.
  - **`summer setup <agent> --yes --json` reports each step** in `steps`: the MCP entry, Summer Games, skills, project files and doctor, each with `ok`, a `status` and, on failure, an `error` with a `code` (`config_invalid`, `config_not_writable`, `skills_install_failed`, `runtime_not_found`, ...). A failed step no longer stops the others, and any failure exits 1. An error before setup starts (an unknown agent, a bad option) is one JSON document too. The output for people is unchanged.
  - **`--runtime <node> --package-dir <dir>`** writes the MCP entry as `<node> <dir>/dist/bin/summer.js mcp` instead of `npx`, in every agent's file format. Setup checks that both exist and that the folder is the summer-engine package. Doctor's skills refresh keeps the bundled runtime.
- **First game: make it look finished.** A first game used to come out as grey boxes: the `make-game` skill told agents to build the first playable from shapes and add art later, and nothing an agent always reads said anything about looks. Now the rule sits where agents read it without choosing to:
  - **MCP server instructions** open with it, inside the first 512 characters (Codex keeps the first 512): keep the features the person asked for and raise the look (sky and sun with shadows, fog, a texture on every surface, real models from the starter project and `summer_assets_search` first, never capsules or boxes as final art, one palette, a styled UI font), then play it and check a screenshot of the running game. They no longer open with "call summer_get_project_context first".
  - **The project's `AGENTS.md` block** (written by `summer create` and `summer setup --yes`) has a "First game: make it look finished" section. It now says to write GDScript files directly and to create scenes and import assets through Summer, and its publishing line matches the store: a game goes live when Summer's automated checks pass, with no wait for a review.
  - **`make-game`:** the first playable already looks good; generation still never blocks the first play (starter and library art first).

## [4.5.0] - 2026-10-19

4.4.0 was not published to npm. 4.5.0 is the first release with everything in it (the [4.4.0] section below), plus these changes.

New since the first 4.5.0 cut: privacy-safe telemetry v2 with a one-time notice, videos (MP4, MOV, WebM) that convert to `.ogv` on import, and a game that goes from export to live over MCP with no staff wait.

- **The `launch-ready` skill: get a game ready to launch and take it live.** Where `release-checklist` reports what is missing, `launch-ready` makes it pass: it exports and uploads the build, captures real gameplay screenshots with `summer_capture_gameplay`, makes the key art, icons, tall cover and capsules from a real capture under the `store-art` rules, writes the store text and fills every listing detail from the project (GameSoul, project memory, README, what it saw in play), runs the checklist again until it passes, shows the creator the preview link, every image and all text, and goes live with `summer_go_live` after one yes. It asks the creator once, before anything is uploaded or spent, for what the project can't tell (price, support contact, developer name, release stage), and has the creator confirm the content rating, the content questionnaire and the AI disclosure. It never invents a fact, never edits a screenshot and picks only true tags, genres and features. Library-only, because the installed-description budget is full: `release-checklist`, `publish-your-game` and `/summer` point to it. It uses only operations the engine profile already has, so the tool count does not change.
- **Telemetry: a few more fields and a one-time notice.** Every field is listed in the README section "Telemetry". Summer never sends prompts, code, file contents, file names or paths, project names, tool arguments or results. `SUMMER_NO_TELEMETRY=1` or `DO_NOT_TRACK=1` turns all of it off.
  - **First run:** the first `summer` command on a computer (`summer mcp` too) prints a one-time notice to stderr and sends one anonymous `cli_first_run` line: a random install id, the command name, the agent app and the operating system. Not in CI. Signing in joins that line to the account.
  - **New fields on signed-in tool-call and command lines, when they apply:** `projectIdHash` (the hash of the random project id the engine already uses for routing; never the project name or path), `templateId` (the catalog template the project started from; on `summer create` also its library domains), `instanceCount` (how many game clients `engine.play` started) and `engineState` (four yes/no facts on `engine_not_running`: engine installed, engine running, project open, signed in).

- **Videos import as Ogg Theora by themselves.** Summer Engine plays video only as `.ogv`, and an `.mp4`, `.mov` or `.webm` import used to fail and roll back. `summer_import_from_url`, its batch, `summer_import_asset_by_id` and `summer_import_asset` now convert a video on the way in: a video Summer generated or stores imports as its Theora rendition from Summer's media host; any other video converts with ffmpeg on this computer when it has Theora (video quality 8, Vorbis audio, same frame rate, at most 1920x1080), else on summerengine.com (needs the Summer sign-in). The `.ogv` lands at the requested path with the extension swapped, and the answer says so (`videoConversions`, `note`). A generated video saved with `out` into a Godot project saves as `.ogv` too. The `animated-loop`, `cinematic-cutscene` and `trailer-shot` skills no longer tell agents to run ffmpeg by hand.

- **From export to live over MCP, with no staff wait.** A game goes live as soon as Summer's automated checks pass; Summer's staff review it afterwards, and no tool or skill tells a creator to wait for a review any more.
  - **`summer_go_live` (`store.go_live`, `summer store go-live`):** releases the uploaded Build to every platform that passed its checks and publishes the store page, through the same store routes Studio uses, then watches until players get it. It needs no owner approval link while the person's Agent permissions allow Publish (the default; otherwise `needs_permission`). Confirm-gated. It answers `live`, `blocked` (each failure with its fix), `needs_changes` (Summer's feedback) or `waiting`; a hold on Summer's side is reported as Summer's, with nothing to fix. Calling again continues without asking twice.
  - **`summer_store_set_details` (`store.set_details`):** the store page sections `store.update_listing` does not edit: the content questionnaire, the AI disclosure, genres, features, credits, language support and system requirements.
  - **`summer_publish_build` waits for Summer's automated checks** and reports each platform (`checks`: passed, or failed with `code`, `owner` and `fix`). A running malware scan is a wait, not a failure. Intake refusals the platform names (`engine_build_unreleased`, `malware_detected`, `verifying_failed` and others) come back with a fix.
  - **`summer.bundle.v2` exports are read.** `summer_export_game` and `summer_publish_build` refused every export from Summer Engine 0.7.4 and newer (the fixed layout); they now take v2 with its six paths and still take v1. `summer_export_game` reports the export's paths.
  - **The `release-checklist` skill:** before going live, check the export (preset, Summer version, the fixed layout, a server pack for a game with a server), the upload and its checks, the store art per slot and every required listing field, each rule with its MCP check, its fix and the platform rule it comes from.
  - The engine profile leaves out the hosted `summer_store_releases` and `summer_store_version_status`, which `summer_go_live` supersedes, so the two new tools fit its tool limit.

From adding Summer to an agent to editing a good-looking scene with one OK: `summer dev` installs the engine (with the person's yes), creates a starter project and opens it; the MCP opens the project itself; agents with no shell use `projects.create_local` and `projects.open_local`; Claude Code Desktop's Browser pane shows the game; and `summer preview` serves the running game to the agent's own browser.

- **`painted-25d-world` plug-in characters are public:** `SummerEngine/painted-characters` (man, woman, man with a sword, old man; 8 directions; idle, walk, run), pinned in the skill with raw-URL imports.
- **`painted-25d-world`: a 1.8 m/s default walk, and a walk clip whose stride fits it.** Cozy, exploration and RPG games walk at about 1.8 m/s and run on Shift at about 4 m/s. The walk cycle's playback stays within about 1.5x its natural speed: when a clip's natural walk is too slow, regenerate it with the brisk long-stride prompt (now the skill's walk prompt, word for word) instead of over-speeding a short-step clip. Stride examples updated to the plug-in sheets (walk 0.94 m per cycle at 1.8 m).
- **`painted-25d-world` after a blind test run and a gait rule.**
  - A first-time agent built a harbour from the skill alone. Its findings are in:
    - a project step;
    - `seedream-5-pro` at 2048x1152 (no Summer image model returns 4K), plus a tiled 4K detail pass;
    - `idempotencyKey` and `numImages: 1` on every generation;
    - a lit blockout capture, and the player set up in capture mode;
    - no CSG;
    - the `.tscn` paint camera line;
    - two-part gable roofs;
    - water blockers and two-sided ground;
    - a 14 m room frame;
    - the upload fields;
    - the plug-in character paths.
  - New building blocks: `blockout_builder.gd` (a JSON blockout spec), `paintcam_check.gd`, and `tools/` (`cam.py` pixel-to-ground, `preview.py` wireframe over the concept, `overlay.py` alignment check, `detail4k.py` tiled 4K pass).
  - Gait: cozy, exploration and RPG games walk by default (about 2 m/s, walk cycle) and run on Shift (about 4 m/s, run cycle). Action games may run by default. Playback stays speed / natural speed.
- **`summer dev` shows the game in Claude Code Desktop's Browser pane.** It adds the `summer-preview` entry to `.claude/launch.json` in the folder it runs in (only adds; never in the home folder; `cwd` set when the project sits below that folder; `--no-launch-json` skips it), so Desktop starts `summer preview` and checks the game after each edit. The `Connected:` line ends with the preview URL (`http://localhost:5199`) and, outside Desktop, `npx -y summer-engine@latest preview --open`. `projects.open_local` does the same for the folder the agent session runs in and answers `preview.url`.
- **Launches and installs, follow-ups from review.** An editor that exits cleanly (code 0) before its API answers is followed when a new editor takes the project over within 5 s (it restarted itself); otherwise it is reported as closed early, never as a broken install. A stale install lock is taken over by one waiter only (an atomic rename, checked). A second `projects.create_local` with no name makes `my-game-2`, `my-game-3`, ... instead of returning the first game.
- **`summer dev [template] [dir]`: from nothing to an editor your agent can drive, in one command.** `npx -y summer-engine@latest dev` installs Summer Engine when it is missing (only with `--yes` or the person's yes at a terminal; an agent without `--yes` gets `needs_confirmation` and the question to ask), creates a starter project (the built-in `3d-basic` unless you name a template) in the project this folder is in, else in this folder when it is empty or only has dotfiles (never the home folder or a filesystem root), else in `./my-game`, opens it in the background with `summer run`'s launch and waits up to 3 minutes for the editor's local API, with a progress line every 10 s. It ends with one `Connected:` line naming the project and the next step. A folder that already holds `project.godot` is just opened, so running it again is safe.
- **The MCP opens the project itself.** When a tool needs the engine and no editor runs, the engine is installed and the session has a project (the agent's folder or `--project`), the local MCP launches it in the background, waits and retries; a slow first open answers "call again in 30 seconds". It never starts a second editor while one is registered for the project, was launched on it and still runs, or does not answer (busy); an editor that exits at once ends the wait, and Linux with no display answers at once. When the agent's folder has no project, it uses the project the last `summer dev` opened from that folder (or below it) while that editor runs, for up to 10 minutes. Otherwise `engine_not_running` names the one step for the case: not installed, ask the person first, then `npx -y summer-engine@latest dev --yes`; no project, `summer dev`; another project open, that project. `SUMMER_AUTO_LAUNCH=0` turns the launch off. The engine-free note names the 4.x tools (`summer_docs_search`, `summer_assets_generate_*`, `summer_jobs_get`, ...).
- **New local operations `projects.create_local` and `projects.open_local`: `summer dev` for agents with no shell** (Claude Desktop, chat apps). `summer_projects_create_local` writes a project from a template (`3d-basic` by default) to `dir`, or to `<name>` next to the session's project, in the session's folder (one of the person's own inside home), or in `~/Documents/Summer` (a chat app's server starts in an app folder); never inside another project. A folder that already holds `project.godot` is left as it is, and a slow template download answers "still creating, call again". `summer_projects_open_local` opens a project in Summer Engine in the background, waits until it connects and binds the session to it; a missing engine is installed only with `install: true`, after the person's yes, and a long install or first open answers "call again in 30 seconds". Both are listed on the v4 surface in the full profile (new toolset `projects`; the capped `engine` profile reaches them through `summer_call`), and run from a shell as `summer projects create-local` / `open-local`. `engine_not_running` now names them next to `summer dev`.
- **`3d-basic` looks like a game:** a procedural sky on a real Environment (ACES tonemapping, ambient light and reflections from the sky), a sun with soft shadows, a tinted ground and one lit hero the camera frames. Before, the sky material was never attached and the scene was a grey box.
- **Pinned templates download without git.** `summer create` (and `summer dev`) fetch the pinned commit's GitHub tarball, compute the same tree digest from the archive and refuse a mismatch, then fall back to `git` only when the tarball path fails. On a Mac without the Command Line Tools this no longer opens their install dialog.
- **`summer install` names why it failed:** `release_info`, `download`, `checksum`, `disk_space`, `mount`, `copy`, `permission`, `app_running`, `needs_confirmation`, `installer` or `unsupported_platform`, in the message (with one next step) and in the usage line, instead of `exit_1`. ## [4.0.0] - 2026-10-15

3.9.0 and 3.9.1 were not published to npm. 4.0.0 is the first release with everything in them (the [3.9.1] and [3.9.0] sections below), plus these changes.

Summer 4.0: every Summer capability is one operation, named `area.action` (`assets.generate_image`, `store.publish`), with one answer shape, and `summer mcp` serves them by default. Engine tools keep their 3.x names. For everything else, `summer_search` finds the operation and its exact input, and `summer_call` runs it. The `summer` CLI runs the same operations.

**To get the 3.x tools back:** start the server with `summer mcp --surface v3`, or add `SUMMER_SURFACE=v3` to the `env` of your agent's Summer MCP entry. That serves the 3.x tools as before. `SUMMER_SURFACE=v3` in your shell also leaves out the new `summer <area> <action>` commands.

**If you signed in with 3.8.0 or earlier,** run `npx -y summer-engine@latest login` once. Generation and the other cloud operations now run on Summer's hosted server, which needs the store sign-in that `summer login` adds since 3.9.0.

### What changes when you update

- **3.x tool names keep working.** `summer_call` runs any 3.x tool by its old name, on the local server and on Summer's hosted server. While the Summer skills `summer setup` installed for your user are older than 4.0, `summer mcp` also lists every 3.x name again (the legacy toolset, local and hosted), each saying which operation replaces it and running as in 3.x. `--toolsets legacy` or `SUMMER_LEGACY_TOOLS=on` keeps them listed; `SUMMER_LEGACY_TOOLS=off` hides them. `npx -y summer-engine@latest setup <agent> --yes` installs the 4.0 skills. With skills from a plugin or a project folder, update them, or set `SUMMER_LEGACY_TOOLS=on` to keep the 3.x names listed.
- **`summer mcp` serves the v4 surface by default** (`--surface v3` or `SUMMER_SURFACE=v3` brings back the 3.x tools). It lists the engine tools under their 3.x names, `summer_docs_search` and `summer_docs_read`, and two new tools: `summer_search` finds any operation, local or cloud, with its exact input, and `summer_call` runs it. Engine operations run here. Cloud operations run on Summer's hosted server, with the same approvals. Every 3.x tool can still be called through `summer_call`, by its old name too.
- **One answer shape.** Every 4.0 tool answers `{ok, status, result}`: `done`, `running` with a job (`jobs.wait` waits up to 50 seconds per call), `needs_approval` with a link for the person, or `dry_run` with a preview. An error has a `code` (`engine_not_running`, `not_signed_in`, `no_credits`, `invalid_input`, ...), a message and exactly one `next` step. Every change takes `dryRun: true` (it changes and spends nothing) and an `idempotencyKey`, so a retry never runs twice.
- **A failed cloud call says what happened.** `not_signed_in` only for a sign-in problem (a revoked or expired store sign-in says `npx -y summer-engine login --store --force`); `forbidden` when Summer refuses the account (for example an unconfirmed email). `unavailable` when nothing reached Summer's hosted server (no connection, the sign-in server down, a 503), or when a read or a dry run was cut off: it is safe to try again. `outcome_unknown` when a change was cut off after it was sent, because it may have run: call it again only with the same `idempotencyKey`, or check first. `--wait` keeps the job id when a wait does not get through. This holds for `summer_call`, the hosted direct tools and `summer <area> <action>`.
- **Approvals.** A change that needs a person answers `needs_approval` with a link (`https://www.summerengine.com/studio/approvals/<id>`) and changes nothing until they approve; `jobs.wait` follows it to the end. Today that covers publishing a game (Summer Games asks the game's owner), price, sale and A/B test changes, member changes, deletes and anything that contacts people. Studio > Settings > Agent permissions lists the defaults; you can change them soon.
- **`summer <area> <action> --field value`** (left out with `SUMMER_SURFACE=v3`). The CLI view of the same catalog, with `--dry-run`, `--wait` (follows a job or an approval to the end) and `--json`. It also adds `summer whoami`, `summer ops search <words>` and `summer ops describe <op>`.
- **Generated files land on this machine again.** On the v4 surface and in the v4 CLI, `assets.generate_image`, `generate_audio`, `generate_3d`, `generate_video`, `generate_motion`, `assets.get` and `jobs.wait` take `out`: a folder or a file path (`res://` in a Godot project). The package keeps it (Summer's server never sees it), downloads each file the answer names and adds `localPath` beside its URL. 3D, video and animation save when `jobs.wait` sees the job finish, also after an approval. Without `out`, a generation in the assets profile or the CLI saves into the project's asset folder: Godot `assets/`, Unity `Assets/Summer`, Unreal `Content/Summer`, three.js `public/assets`. `assets.get` saves only with `out`, and sessions with engine tools save only with `out`, because `summer_import_asset_by_id` already puts the file in the project. A save never overwrites a file (it takes the next free name and says so), writes only media and model file types (never `.cs` or `.dll`), keeps `res://` inside the project, downloads only from public https hosts, up to 500 MB. Whatever is not saved is a warning; the answer stays as it was.
- **The assets profile on 4.0.** `summer mcp --profile assets` (what `summer setup <agent> --assets-only` writes) lists Summer's hosted asset reads and generators, jobs and `whoami` as direct tools, plus `summer_search`, `summer_call` and the docs tools, and its instructions name only tools it lists. Generators run on Summer's hosted server by their 4.0 names; a 3.x generator name called through `summer_call` still runs the local 3.x tool.
- **Skills use the 4.0 names.** The asset, publishing, plans, Summer Apps and Studio skills name the operations (`assets.generate_image`, `store.publish`, `plans.create`, `apps.call`, `studio.open`), every skill and reference names the docs tools `summer_docs_search` and `summer_docs_read`, and the asset skills save files with `out`. `validate:library` fails when a skill or reference names a 3.x docs tool. Engine tools keep their names.
- **The docs describe 4.0.** README, AGENTS.md and `docs/` now say how to connect (one hosted URL and one sign-in for cloud work, the local server for engine work), how agents call Summer (operations, `summer_search` and `summer_call`, one answer shape and its error codes, 3.x names that keep working), what an agent may do on its own (Agent permissions, approvals, Agent activity), how credits and auto top-up work, the two store versions for ChatGPT and Claude's connector directory, and the `summer <area> <action>` CLI.
- **`summer_run_script` takes `scenePath` and is stable.** The script runs against the scene you name: Summer opens it first (on its own, never in a batch with an edit), runs the script, then opens the scene you were looking at again. If the scene cannot be opened, the script does not run. The result says what happened in `scene_target`. Without `scenePath` it runs against the open scene, as before.
- **Engine operations in the 4.0 catalog.** Every engine tool keeps its 3.x name and is now an operation with a title, a summary of 300 characters or fewer, its effect and an example (`src/core/ops/engine.ts`). On the v4 surface each engine tool lists that summary plus a pointer to its full guide, its hints come from its effect, and it answers in the one answer shape: `{ok, status, result}`, or one error code with one next step (`engine_not_running` says to open the project, instead of plain text). The v4 engine tools list takes about half the tokens of the 3.x one.
- **Each engine tool has a guide.** `summer_docs_read` with id `tool/<slug>` now also returns the tool's full how-to (`library/tools/<slug>/GUIDE.md`, the text the 3.x MCP description carries). `npm run generate:tool-guides` keeps the two the same.
- **Reads split from changes.** `summer_camera_bookmark` becomes `engine.list_camera_bookmarks` (read), `engine.save_camera_bookmark` and `engine.delete_camera_bookmark`; `summer_ui_actions` becomes `engine.list_ui_actions` (read) and `engine.invoke_ui_action`. On the v4 surface each is its own tool; the 3.x tools stay as they are.
- **`summer_call` for engine operations**: a dry run checks the input without the engine, `ops.describe` answers for local operations here, and a bad input points at the tool's guide.
- **Skills teach one script for multi-step scene work.** 28 code blocks in 23 skills chained 4 to 15 single scene edits (`summer_add_node`, `summer_set_prop`, ...), 197 calls in all; each is now one `summer_run_script` call with `scenePath` (the kit-placement example is one `summer_batch`). `scene-scripting` is stable and under 200 lines, with the extended ctx API and the recipes in its `references/`. AGENTS.md, `/summer`, `using-summer`, `make-game` and the agent playbook say it once each: 3 or more scene edits are one `summer_run_script` with `scenePath`. 46 script lines in 10 skills that wrote `var x := ctx.…` (which does not compile: `ctx` is untyped) now write `var x = ctx.…`. `validate:library` fails on a code block with 4 or more single scene edits (unless the line before it says why with `<!-- single-edits-ok: … -->`) and on `:= ctx.`.
- **The operation contract.** `registry/schemas/operation.schema.json` describes an operation (name, effect, approval, input, output), and `registry/operations/legacy-names.json` maps every 3.x tool name to its operation (`summer_set_prop` is `engine.set_prop`, `summer_store_submit` is `store.publish`). Conformance fixtures sit next to it.
- **Official MCP Registry.** `package.json` names the server `io.github.SummerEngine/summer` (`mcpName`), and the generated `server.json` lists the npm package and the hosted server. The name keeps the GitHub org's own case, because the registry matches it exactly against the org.
- **The hosted 3.x tools ask for 3.x.** The local server mounts Summer's hosted 3.x tools (the 3.x surface and the legacy toolset), and `summer tool` and `summer doctor` call them, with `?surface=v3`, so they keep their 3.x names when Summer's hosted server serves 4.0 by default.
- `summer doctor` checks for the tools of the surface `summer mcp` will serve (`summer_search` and `summer_call` on v4).
- The per-call usage line also says which operation the call ran, the surface (`v3` or `v4`) and the profile. It never sends arguments or results.

### Also in this release

- **Setup never pins an older release.** When the CLI that runs `summer setup` was newer than npm `latest`, setup wrote `summer-engine@next` into the agent's MCP entry. `next` had stayed on 3.1.0, so the agent ran a release from September and silently lost `--assets-only`, `--profile` and every newer option. Setup now writes `next` only when `next` is this exact version; otherwise it pins this exact version (for example `summer-engine@4.0.0`), and a build that is not on npm keeps `latest` and says to use `--local-dev`. `--channel` (and `SUMMER_CHANNEL`) accepts an exact version, and the refresh command `summer doctor` prints follows the same rule.
- The release steps (`docs/NPM_PUBLISH_QUICK_COMMANDS.md`) now point `next` at every new `latest` release and create the `v<version>` tag and GitHub Release from the CHANGELOG.
- The `summer` banner no longer prints colour codes when `NO_COLOR` is set or the output is not a terminal (a log, a pipe, an agent's shell).
- `summer setup notanagent` now says the agent name is unknown and lists the supported ones.
- `summer setup codex` writes the MCP entry to `$CODEX_HOME/config.toml` when `CODEX_HOME` is set, where Codex reads it.
- `summer setup <agent>` without `--yes` says to run it again with `--yes` to install the skills, instead of printing an internal command.
- `summer setup` prints the first few installed skill names and how many more, not every name; `--json` still lists them all.
- `summer_open` is marked as reaching outside the machine (`openWorldHint`), because it opens summerengine.com pages in the browser.
- **The README starts with Connect.** Summer's hosted server, `https://mcp.summerengine.com/mcp`, comes first, with one install line for Claude Code, Codex, Cursor, VS Code, Devin Desktop and Claude Desktop (plus one-click buttons for Cursor and VS Code), then the local `npx -y summer-engine@latest mcp` server. The assets-only path offers the hosted server too, names the file formats (GLB, PNG, JPG, WebP, MP3, WAV, MP4) and says how to download a file for any engine or web app. The long agent install playbook is folded away on GitHub; agents still read all of it.
- **The docs describe the shipped product.** Publishing to summer.games and Grow are listed as available, not "preview" and "planned", and the "not promised" note is gone. `tool/export-game`, `tool/publish-build`, `tool/capture-gameplay`, `skill/multiplayer-publish` and `skill/summer-analytics` are stable, and the tool reference lists the hosted store, publishing and Grow tools. (This carries over #97.)
- **Fixed wrong statements:** `summer login` waits up to 15 minutes, not 120 seconds; AGENTS.md says publishing is `summer_publish_build` and then the owner's approval through `summer_store_submit` (the old creator command is gone); generation tools spend credits when they are called, so the README no longer says Summer never spends without a confirmation; the development guide no longer lists the removed `summer publish` and `summer releases`; the store sign-in files (`oauth-token`, `oauth-client`) are in the `~/.summer/` lists; GEMINI.md uses bare skill names. Every setup guide uses the same paste prompt and installs every skill (`--recommended` is the smaller opt-in set).
- **`summer doctor` needs Node 20,** the same as the package's `engines` field. It accepted Node 18 before.
- **Community files:** CONTRIBUTING.md, SECURITY.md (report privately through GitHub), CODE_OF_CONDUCT.md, issue forms for bugs and library entries, and a pull request template.
- **CI** also builds and runs the CLI on macOS and Windows (Node 22) and on Node 20, runs with read-only permissions, and drops the old `v3-foundation` branch and the example-eval step that only printed SKIP.
- **Fewer skills in every session.** The library-author skills (`skill-create`, `skill-improve`, `skill-test`, `writing-skills`) and the six research digests (`celeste-momentum-platforming`, `godogen-visual-proof-game-generation`, `lumera-single-image-scene-reconstruction`, `realtime-wet-surfaces`, `psx-retro-rendering`, `skintokens-auto-rigging`) no longer install with `summer setup` or the plugins. They stay in the library: `summer_docs_search` finds them, `summer_docs_read` reads them, and `summer skills install <name>` still installs one. Copies from an earlier setup stay until you delete them. A new `bundled: false` field in a skill's `resource.yaml` does this.
- **Skill descriptions fit the hosts again.** Hosts put every installed skill's description into every session and cut what does not fit. The installed descriptions now total about 11,500 characters, down from about 17,300, and `npm run validate:library` fails when they pass 12,000. Library search ranks the same on the routing eval.
- **Skill links work after install.** `summer setup` copies each skill folder alone, so 40 links like `../../references/mcp-tools-reference/mcp-tools-reference.md` (and 4 links into other skills' folders) were dead in the default install. They now name the library id to read (`summer_docs_read` id `reference/mcp-tools-reference`), and `validate:library` rejects any path that climbs out of a skill folder.
- **Call examples are complete.** 65 call examples in ui-basics, 3d-lighting, design-level, design-npc, game-feel, art-direction and summer-apps left out a required argument, mostly `scenePath`, which the tool rejects. Each now passes it. `validate:library` checks every `summer_*` call example in the skills against the tool's `input_schema` (required arguments present, no unknown ones) and prints how many it checked.
- **Errors carry a stable code.** When the engine is not running, the person is not signed in, the account has no credits or a Summer service cannot be reached, every tool now answers `{ok: false, code, error, recovery}`: `code` is `engine_not_running`, `not_signed_in`, `no_credits` or `unavailable`, the same codes the 4.0 tools use, and `recovery` is the one next step. The fields each tool sent before (`message`, `hint`, `status`) are still there. Generation, job, asset and Summer Apps tools used five different sign-in answers; they now use this one. The store sign-in keeps its own code, `store_login_required`.
- **The engine-down answer works.** It told agents to run `npx -y summer-engine@latest run`, which fails without a project path. It now says to open the project in Summer Engine or run `summer run <project-path>`, and no longer shows token-file details. `summer tool` prints the same fields as JSON (exit 1) instead of saying "not running" twice.
- **Network errors keep their cause.** "fetch failed" now says why, for example `connect ECONNREFUSED 127.0.0.1:443`, in the message and in `details.cause`.
- `summer_list_my_assets` no longer says "Asset search requires an account" when you are not signed in.
- **3D and motion generation return a job id at once.** `summer_generate_3d` and `summer_generate_motion` used to hold the agent for up to 10 minutes while the job ran. They now return the `jobId` within seconds, the same as Summer's hosted server, with a `next` line that says to poll `summer_check_job` until the status is `completed`. `wait: true` still blocks for scripts that cannot poll. `summer tool generate-3d` and `summer tool generate-motion` work the same way.
- **The assets profile no longer points at engine tools.** With `--profile assets` (and `summer setup --assets-only`), `summer_get_agent_playbook`, the `summer_agent_playbook` prompt and `summer_start_game_task` told the agent to call `summer_get_project_context`, add nodes, play and take screenshots, none of which that profile has. They now answer with a no-engine version: ask what the asset is for, reuse before generating, confirm the spend, wait for the job, check the preview, and hand the file over with `summer_get_asset_download_url` (or `out` on `summer_generate_image`). The plan only names tools and skills the profile has, and says when a task needs the full setup instead.
- **A session skill for the assets path.** The new `summer-assets` skill replaces `using-summer` in the assets-only install: what the session has, the loop, the file formats, and when an asset is done. `store-art` (Summer Games store art) left that install too.
- **Every asset skill says what to do without Summer Engine.** The 23 skills in the assets-only install each have a short "Without Summer Engine" section: which steps to keep, which import and scene steps to skip, and how to hand the file over. A test fails when an asset skill has none.
- `summer skills install --assets` (and `setup --assets-only`) no longer copies the Claude Code commands `/start`, `/summer` and `/gameskill`, which start and route engine work.
- `summer_store_tools` names the tools it loads in the current profile (the Tool Factory and asset editing tools in `assets`, the store and publishing tools in `engine`) and carries its own tool hints and title.
- `generate-motion` and `text-to-motion` no longer say `wait: true` is the default.

Not published to npm: these changes ship in 4.0.0.

3.9.0 was not published to npm; 3.9.1 is the first release with everything in 3.9.0 below, plus these changes.

The Claude Code plugin gets a first-run guide and Summer's hosted server, and passes `claude plugin validate --strict`.

- **`/summer:start`.** A new command for the first run: it checks what is on the machine, signs the user in, and gets a first game playing in about five minutes, from a template that already plays or from a board of concept art Summer draws in the chat (the hosted `summer_make_game`), built in the Summer Engine desktop app.

The plugin no longer names `hooks/hooks.json` (its default location) or declares the pre-commit doctor option, which opened a settings dialog on enable; `SUMMER_PRE_COMMIT_DOCTOR=1` still turns that hook on. The repo's own `CLAUDE.md` moved to `.claude/CLAUDE.md`, because a `CLAUDE.md` at the plugin root fails the strict check.
- README and `docs/CLAUDE_CODE.md` show the one-line plugin install: `/plugin install summer --marketplace summerengine/summer`.
- The once-per-session usage line now names your agent app (the name it sent in the MCP handshake) and goes out on the first tool call of any kind, not only the first engine tool. `SUMMER_NO_TELEMETRY=1` or `DO_NOT_TRACK=1` still turns it off.

## [3.9.0] - 2026-10-14

One sign-in for every Summer tool, tool profiles that fit every agent, shorter tool results, and Summer sees which agent app made each request.

- **Summer sees which agent app made each request.** Every request to Summer's servers (generation, jobs, assets, Summer Apps, the store upload, the hosted Summer Engine MCP, library search and the usage line) now carries the agent app's id (`X-Summer-Agent-Host`, for example `claude-code`), the name and version the app sent in the MCP handshake, and the tool that made the request (`X-Summer-MCP-Tool`). Before, the app was never sent. Outside an MCP session (`summer tool`, `summer login`) the id comes from the agent's environment; `SUMMER_AGENT_HOST` overrides it. `SUMMER_NO_TELEMETRY=1` or `DO_NOT_TRACK=1` removes these headers and keeps only the CLI's own name and version.
- **One sign-in.** `summer login` now signs you in to your Summer account and then, in the same browser, to the store, publishing and Grow tools: one Allow click, or none if this machine was approved before. Before, that took a second `summer login --store`. If the store step does not finish within 3 minutes, your account sign-in is kept and `summer login --store` adds the store later. `summer login --no-store` skips the store step; `summer login --store` still runs it alone.
- **Every tool says what it does.** Each local MCP tool now carries `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint`, mapped from its `authority` in the library. Agents and apps that ask before a change can let reads run and still ask before an edit, a generation that costs credits, or a publish. A test fails when a tool has no hints.
- **Agents script runs of scene edits.** The MCP instructions now say: more than 3 scene edits, write one `summer_run_script` (snapshot, script, diff, screenshot). After the 4th single edit in a row (`summer_set_prop`, `summer_add_node`, `summer_remove_node`, ...), the result adds one line that points to `summer_run_script`, then again every 6th.
- **Tool profiles.** `summer mcp --profile` (env `SUMMER_PROFILE`): `full` is every tool and stays the default, so existing setups do not change. `engine` has the engine, generation and store tools and stays under 128 tools; `summer setup vscode-copilot` now writes it, because VS Code Copilot takes at most 128 tools per request (`--profile full` keeps every tool). `assets` has generation, the asset library, account and library search, and no engine tools. `--toolsets` (env `SUMMER_TOOLSETS`) adds toolsets by name. Engine tools load at start in every profile that has them, and no tool is renamed.
- **Assets-only setup.** `summer setup <agent> --assets-only` writes the `assets` profile, installs only the asset skills instead of the whole library, and leaves out Summer Games. The README's assets-only path now uses it. `summer skills install --assets` installs the same skills.
- **Shorter results.** Tool results are compact JSON instead of pretty-printed JSON. Results that can be long (scene and runtime trees, console and debugger reads, inspect reads, library reads) stop at a default size and say so: 4,000 characters, 8,000 for `summer_get_scene_tree`, 24,000 for `summer_read_library`. Pass `maxCharacters` for more. Writes, job ids and file reads are never cut.
- **Usage reports.** When you are signed in, the MCP server now reports each tool call to Summer: the tool name, whether it worked, how long it took and your agent app's name. Nothing else: no arguments, results, code or file names. `SUMMER_NO_TELEMETRY=1` or `DO_NOT_TRACK=1` turns it off, and now also turns off the once-per-session report.
- `summer_app_guide` starts with section `overview` by default and answers Markdown text instead of one long JSON line; `all` still returns every section.
- `summer_app_screenshot` takes `steps` (click a selector, press a declared action, wait) to show a dialog or a second state before the capture, and waits until the app's calls settle.

## [3.8.0] - 2026-10-13

Agents build Summer Apps, team tools inside Summer Studio, and asset-only requests skip the engine.

- **Summer Apps tools.** A Summer App is a tool your team uses inside Summer Studio: a balance table, a quest editor, an asset tracker, a pick-one grid. Your agent builds it and it works on the team's data. New tools: `summer_app_guide` (the build guide), `summer_app_list`, `summer_app_create`, `summer_app_publish` (from a local folder, files or a layout), `summer_app_get`, `summer_app_events` (what the app sends to agents), `summer_app_page` (fill the app's fields and press its buttons), `summer_app_data` (read and write the app's shared data; `as: "seed"` for starter data), `summer_app_tools` and `summer_app_call` (the agent tools an app declares), `summer_app_dock` (dock an app as a panel in the editor) and `summer_app_report_gap` (tell Summer what the app needed and did not have). All but `summer_app_dock` work without the engine; they need `summer login`. If Summer Apps is not open for your account yet, they answer `not_found`.
- **Two new skills: `summer-apps` and `summer-apps-design`.** `summer-apps` is the build loop, Layout or code, the manifest, the SDK, data and agent tools, with a complete working app. `summer-apps-design` is how an app should look: page layout, the Summer UI kit components, tables, charts, states, and a check before you publish.
- **`summer_app_screenshot`: see your Summer App without opening Studio.** Summer renders the app's published version with your data and returns the picture plus what to fix: console lines, uncaught errors, calls it refused, whether the SDK connected, and the fields and buttons the app declared. It is read-only: writes, sends and paid calls are refused, so nothing changes. `width: 390` shows the phone layout, `theme: "dark"` the dark theme, `fullPage` the whole scroll; `out` also saves the PNG (`summer tool app-screenshot` saves it to `./summer-app-screenshot.png`). The `summer-apps` skill now looks at every publish this way.
- `summer_app_create` without `workspaceId` puts the app in the person's team: the one their Studio tab is on, else their latest team, else their personal workspace. The result says which.
- `summer_app_events` waits up to `timeoutSeconds`, the same argument name as the hosted tool.
- `summer_app_guide` has section `types`: the SDK's exact TypeScript types. Keep that file one folder above the app; a `dir` publish also skips `.d.ts` files.
- **`summer_app_update`** renames a Summer App or sets it kept, archived or back to scratch, so agents archive the throwaway apps they made.
- **`summer_enable_plugin` enables an editor plugin (`res://addons/<name>/`) and reports what really happened.** On engines that wait for the plugin, it answers `enabled` with the plugin's autoloads, or the failure code with a hint. Older engines only queue the enable; the tool then answers `queued: true` and `enabled: null` with a note, and does not claim success.
- Hosted tools such as `summer_studio_page` no longer fail with "Tool not found" when an agent calls them right after it connects, before it lists the tools. The call now waits for the hosted tools to finish loading, then runs.
- **Assets only: no engine, no brainstorm, one sign-in.** If you only want assets (a sound, an image, a model), the README has a prompt to paste that skips the engine download and the starter project, and runs setup with `--no-games` so you sign in once. `/summer` sends an asset request such as "make me a sword clash sound" straight to its asset skill instead of a game brainstorm, and `sound-effect` stops after you approve the clips when there is no project to import into.
- Out of credits, a generation tool now gives one link: the Add credits step in Summer Studio (`https://summerengine.com/studio/credits`). Pick an amount and pay once; no plan needed.

## [3.7.0] - 2026-10-13

Every result is under 5 KB, names its evidence (`visual_aabb`, `physics`, `mesh_triangles`, `markers`) and declares any cut list:
  - `summer_inspect_asset`: measure a `.tscn`/`.glb`/`.gltf` (or Mesh) without adding it to a scene. A `summary` block comes first: AABB, origin label, the two largest opposite plane pairs with a `one_sided` flag per plane (its material culls back faces) and the ids of port-like open loops. Then per-mesh AABBs and triangle counts, the 6 largest planar faces, open boundary loops, Marker3D anchors, collision shapes. Open loops have stable ids by facing and position (`+Y` = the outermost loop facing +Y in the piece's own axes, `+Y#2` the next), never by radius, so the same id names the same loop in every pose. `detail: "summary"` (default) lists only port-like loops (radius over 2 cm with a partner loop facing another way, or the one opening of an end piece such as an outlet's socket), so a flat wall's outline no longer buries the facing; `detail: "full"` lists every loop. `maxTriangles` goes down to 100, and the summary says which budget covers a mesh the budget cut.

The piece keeps its height and place along the surface (`placeAt: "current"`) unless `placeAt: "hit"` slides its back-face centre onto the ray hit. Before saving it refuses, and puts the piece back exactly where it started, when the seat lands on another node than the named surface (or, with a ray only, off the hit plane) or the piece would move more than `maxMove` (default 2). The receipt names `seated_on`, `final_gap`, `back_face_gap` and `moved_by`; a failed seat adds `blockers` (what the piece overlaps, whether it started overlapping, the first contact) and a `next_step`.

### Fixed
- `summer_scene_audit`:
  - `transform` no longer flags correctly placed pieces whose global origin is the world origin. A piece is "left at the origin" only when its LOCAL transform is identity, its parent's is identity, it touches nothing and it is not one of a row of siblings. Several pieces sharing that transform are a warning each; one alone is a look item.
  - Screen-space quads (a post-process `extra_cull_margin` or a huge `custom_aabb`) are skipped. They were "sunken" and "at the origin".
  - `z_fight` evidence names the shared plane's `normal` and the axis to nudge (`nudge.world`, `nudge.local`), so a window insert whose head or jamb is the shared plane is not nudged along the facade normal.
- Seeing tools (preview):
  - Camera poses behind one-sided walls. The visibility pass now reads which side of each surface a ray meets (a short front-faces-only ray at the hit). A sight line that crosses a hard or subject surface from behind blocks like a wall, unless the material is transparent. A frame that is more than 25% surfaces seen from behind is rejected as `behind_surface`. So is a lens inside a closed shell (`inside_volume`) or within 0.3 m behind a back face. This removes `summer_frame_shot` corridor winners that stood behind a back wall and looked through its door hole.
  - `summer_frame_nodes` with an explicit `from` measures that exact pose plus about 20 nearby alternatives (wider lens, turned, raised or lowered). If walls block it, or it stands behind or inside a surface, the caption opens with a WARNING and the nearest valid `from` (+ `fov`). The requested view is still rendered. `receipt.view_check` carries the result.
  - Marks no longer pass off hidden nodes as visible. `summer_frame_nodes marks:true`, `summer_screenshot marks:true` (3D scene) and `summer_zoom mark` test each labelled node from the rendered camera (centre plus 4 points across the box face it shows). Hidden labels are noted `(hidden behind <path>)`, and a zoom on a hidden mark warns.
  - `summer_zoom` honours the region exactly. The region is no longer grown to 16:9 or padded by default. The image takes the region's own aspect, with dark bars only past 0.5-3.2. The caption reports the real zoom per axis and `widened_because`. `pad` defaults to 0 for `region` and to 0.15 for `mark`.
  - Establishing shots:
    - the top 3 are three different views: one per side of the subject while the score is within 0.15 of the best, and always at least 25 degrees apart. This also applies to low-angle and detail shots; eye-level looks are spaced 25 degrees apart;
    - a `light` term reads the strongest DirectionalLight3D: side or front-side light scores best, light from straight behind the camera (a flat-lit face) worst;
    - an `edge` term penalises sky or void below the horizon from 4% of the frame;
    - a `solid` term counts surfaces seen from behind.
  - `summer_frame_shot` eye-level and corridor cameras stay at eye height. Corridor winners could come back "adjusted: raised" well above eye height: the candidates included 2.4 m and 3.5 m eyes, and the ground-clearance check read a duct or balcony overhead as ground and lifted the camera over it. Now every eye-level and corridor pose stands 1.5-1.8 m (or exactly `eye_height`) above the walkable surface straight below the lens, within a step of the spawn's or corridor's floor, and is never raised. A pose that cannot stand there moves horizontally (along the view, then sideways) or is rejected (`no_walkable_ground`, `not_walkable`; a raised or off-height pose is `raised_above_eye` / `above_eye_height`). The corridor scan seeds on the walkable floor inside the subject (a 7 x 7 grid of downward rays from the subject's middle; the most common horizontal surface met from above with headroom for an eye wins) instead of the subject's lowest point, which walls sunk into the ground put under the floor. The caption and `receipt.scan_floor` say where it seeded, and a fallback to the lowest point is declared.
  - Establishing shots rank in tiers: a pose showing more than 15% empty ground (featureless ground or surroundings outside the subject's footprint, from the image check) or world edge ranks below every pose showing less, whatever its score.
  - Every `summer_frame_shot` top pose and tile label states the real camera height: metres above the first surface below it and the absolute y (`receipt.top[].camera_y`, `ground_y`, `height_above_ground`).
  - Transparent materials (alpha blend, scissor, hash, depth pre-pass, shaders that write ALPHA, instance fade) no longer block like walls. They get their own physics layer, outside every sweep. A sight line through them counts 0.8, and a grid cell counts half a soft cell. Meshes that mix opaque and transparent surfaces are split per surface.
  - `summer_shot_sheet` without `compare_previous` no longer overwrites each bookmark's previous image (the compare baseline). The same rule now holds for `summer_debug_views` and `summer_screenshot framing:"bookmark"` (MCP and `summer tool`). A plain render creates a missing baseline and keeps an existing one, and says so. Only `compare_previous:true`, the new `update_previous:true`, or re-saving the pose with `summer_frame_nodes` / `summer_frame_shot` replaces it.
- `summer_snap_to_surface` could not seat a prop sunk into its support: the engine backs a start overlap off, sweeps, then measures `hitTravel` from the original pose (negative when sunk) and refuses with `gap_exceeds_hit_travel`, so agents set the height by hand. When the subject starts inside its support the tool now lifts it against the cast direction by the overlap depth plus 2 cm (at most the subject's extent and 0.5 m; exact local position from the saved scene, mapped through the parent transform), snaps again, and keeps the result only when it settles on a node it was sunk into; otherwise it restores the original position. The receipt carries `recovery` (`lifted_by`, `original_local_position`).
- `summer_snap_to_surface` failed on props without colliders: collider-less ferns on a ground PlaneMesh all answered `overlap_recovery_exceeded`, "starts in contact with or inside (unnamed)". Without a collider on the subject or the support the engine falls back to `visual_aabb`, the subject's AABB swept against every other visible AABB, and one big AABB around it (a tree, a block, a post quad with a huge custom AABB) is an overlap no back-off clears; a seat can also rest on an AABB above the real surface. Whenever the engine answers with `visual_aabb` (that failure, `gap_exceeds_hit_travel`, `surface_not_found`, or a seat) a read-only probe measures the move from visible triangles: the subject's vertices cast along the direction onto the triangles of the meshes below (a surface through the subject means it is sunk and is lifted out, at most 0.5 m), plus the support's vertices under it cast back onto the subject. One SetProp places it, a second read verifies the gap (undone beyond 5 mm), and the scene is saved: `evidence: visual_mesh`, with the engine's answer under `engine`, `verify`, and `evidenceDetails` (samples, triangles, colliders). Screen-space meshes (a shader that writes `POSITION`) are not surfaces. When the triangles find no support either, the engine's failure comes back with `mesh_fallback`.
- `summer_snap_to_surface` failures `gap_exceeds_hit_travel` and `overlap_recovery_exceeded` said nothing about why. A read-only starcast at the current pose now adds `start_overlap`, `blocking` (the nodes the subject touches or sits inside), `below`, and a concrete `next_step`, also in the error text. Same implementation on `summer tool snap-to-surface`.

The engine's ReplaceNode routes through the editor's "Change Type" path, whose `Node::replace_by` copies the old node's `scene_file_path` onto the new instance. The tool now saves, reads the saved scene, and swaps through ops that persist: InstantiateScene under a temporary name, SetProp for each property override (transform, visibility, ...), ReparentNode for each child the scene added (re-owning deeper descendants the engine's ReparentNode leaves unowned), MoveNode to the old index, RemoveNode, rename, SaveScene. ## [3.0.0] (2026-09-09): "The Library"

v3 rebuilds the package around one idea: every resource is described once (`library/<kind>/<slug>/resource.yaml`) and everything else (the searchable index, every agent manifest, the skill and template registries, counts, aliases) is generated from it, with CI failing on drift. Migrating from v2: `docs/MIGRATION-V2-V3.md`. The design contract and the verified-vs-planned status live in the repository under `docs/design/`.

## [2.8.1] (2026-08-18): "Scene mutations work again on engine 0.5.60+"

### Added
- `summer_get_scene_tree` accepts optional `depth` and `limit` params (engine defaults: depth 2, limit 200; a 102-node scene silently truncated to 61 nodes at the defaults). The engine only honors them on scene-targeted reads, so the tool resolves the current scene path first when needed and says so when it can't. `summer_get_project_context` accepts an optional `settingsPrefix` and, without one, trims `project.data.entries` to a curated prefix set (application/, display/, input/, physics/, rendering/) instead of returning the full ~188KB settings dump; the payload declares the trim via `settingsTruncated`/`totalSettings`/`settingsHint`.
- `summer_screenshot` scene captures accept `nodePath` (frame a specific node, honest `node_not_found` failure) and new framing directions `back`/`left`/`right`; captions report the resolved framing and any render retries. Requires engine 0.5.62+ to take effect; older engines silently ignore the new fields.
- `summer_get_diagnostics` returns a prioritized bounded view (errors first, then warnings, capped info tail) with honest suppression counters, plus `includeAll: true` for the untrimmed payload. Severity + recency + caps only, no noise-pattern matching.
- `scripts/compat-smoke.sh`: a latest-MCP × candidate-engine release gate that drives the real built MCP server against a live engine and fails loudly on batch-contract incompatibilities (the class of bug that broke 2.7.0–2.8.0 × engine 0.5.60+). Run it before every engine release and every npm publish.

### Fixed
- `summer_create_scene` no longer uses the destructive temporary-template strategy (open current scene → delete its children → save-as → restore). It now writes a minimal `.tscn` through the identity-bound engine `WriteFile` with a create-only guard, never touches the open scene, verifies by reading the file back, and gained a `rootType` param (Node3D/Node2D/Control). `allow_temporary_scene_mutation` remains accepted as a deprecated no-op.
- **Scene mutations were completely broken against engine 0.5.60/0.5.61.** The engine now requires `SaveScene`, `InstantiateScene`, `ReplaceNode`, `SimulateInput`, and the `Run*`/`Import*`/`Git*` ops to travel as their own single-op request, and rejects any multi-op batch containing one of them wholesale (`failure_reason: "unsupported_transport"`). Since 2.7.0 appended `SaveScene` to every mutation batch, every `summer_add_node`/`summer_set_prop`/`summer_batch`/`summer_create_scene` call was rejected before anything executed. Mutation batches are now automatically split into sequential requests around single-only ops; all receipts are preserved and merged, and a mutation that applied followed by a save that failed is reported honestly (including which ops already applied and which were not sent).
- Engine failures no longer hide the precise rejection. `extractOpError` previously returned a generic `"Engine operation failed (terminalState: failed)"` without inspecting `results[]`; it now surfaces the failed op's own error and `failure_reason` (envelope or per-op, either spelling), rendered as JSON when a classifier is present so agents can key on `failure_reason` reliably.
- `save_frame` is documented with its required `name` argument everywhere (`save_frame()` with no args is a probe script error), plus the deferred scene-mount pattern that avoids black frames.
- SimulateInput guidance corrected: it IS reachable over MCP/CLI as a single op against the running game (`failure_reason: "not_running"`/`"unsupported"` are the real failure modes); `"unsupported_transport"` only means it was batched with other ops. The previous claim that it needs the in-editor bridge on every build was stale.
- The scene-preview synthetic-camera note no longer claims the scene has no camera; the engine always synthesizes the preview camera; `sceneHasCamera` is the authoritative signal and keeps its own warning.
- `summer login` waits 15 minutes on one session id (was 2) with periodic reminders, covering first-time account creation + email confirmation. The gateway never expires a pending session, so the single id stays valid the whole window.
- Removed the stale "Engine mirror only" banner from the README (it shipped to npm and the public repo, and its claims were wrong).

## [2.7.0] (2026-07-24): "Reliable project mutations"

### Added
- `summer_read_file`, `summer_write_file`, and `summer_replace_text` expose engine-routed project file access, including `.tscn` and `.tres`. New files require `create_only:true`; overwrites require an engine sha256 receipt.
- File mutations fail closed unless the MCP client has a complete engine/project identity and use the bound project hash even if caller options attempt to override it.

### Changed
- Agent playbooks now route project file mutations through Summer MCP instead of recommending host writes that bypass identity, content guards, and editor reload handling.
- Scene mutation tools require an explicit `scenePath`; the target scene does not need to be the visible editor tab.
- `summer_open_scene` is navigation only and no longer acts as implicit mutation targeting.
- Dedicated scene mutations and mutation batches append one final `SaveScene` at the transaction boundary.
- Agent guidance no longer claims that routine scene edits require stopping the running game.

### Fixed
- Bridge/project identity rejections now return one correlated `not_sent`
  terminal, allowing the web harness to retry safely instead of waiting for a
  mutation receipt that cannot exist.
- Same-file MCP mutations now serialize the complete read-to-write transaction,
  preventing concurrent replacements from racing on a stale file preimage.
- Accepted engine operations preserve their request identity and report whether
  they are still queued, still running, or uncertain instead of claiming that
  nothing was applied after a client wait deadline.
- `summer_batch` no longer permits raw file mutations that bypass the guarded
  `summer_write_file` and `summer_replace_text` tools.
- Scene operations return target/persistence evidence and concrete dependency errors instead of relying on ambient open-scene state.
- Asset placement reports success only after both the import and explicit target-scene mutation are confirmed.

### Limitations
- The package cannot intercept an external agent's native filesystem tools. A host can still mutate files outside MCP, and a non-atomic external write can race the engine between validation and write; those cases remain technically unenforceable.
