# Migrating from Summer v2 to v3

Short version: **users do nothing.** MCP configs run `npx -y summer-engine@latest`, so the code updates itself on the next session. Agents with installed skill snapshots re-run one command to refresh them:

```bash
npx -y summer-engine@latest setup <agent> --yes --force
```

(`summer doctor` flags a stale snapshot via `skills-version-stale` anyway.)

## What v3 is

v3 rebuilds the repo around one idea: **every resource is described once, and everything else is generated.** The rules live in [`design/CONTRACT.md`](design/CONTRACT.md), the reasoning in [`design/DECISIONS.md`](design/DECISIONS.md).

## What moved

| v2 | v3 |
|---|---|
| `skills/<category>/<name>/SKILL.md` | `library/skills/<slug>/` — flat, with a `resource.yaml` descriptor; categories became metadata facets |
| `references/*.md` + assorted docs | `library/references/<slug>/` |
| Hand-written plugin manifests (`.claude-plugin/plugin.json`, `.codex-plugin/…`, `gemini-extension.json`, …) | Generated by `scripts/generate-registry` from `library/`; the root files are build artifacts |
| TS `SKILL_REGISTRY` (hand-maintained) | `registry/generated/skills-registry.json` (compiled) |
| `references/template-registry.md` + cloning a template repo's default branch | `library/templates/<slug>/resource.yaml` pin manifests — exact commit + tree digest, recorded into the project (`.summer/project.json`) |
| Tool/skill counts written by hand into docs | `registry/generated/counts.json`; CI fails docs that contradict it |

## What stayed exactly the same

- Your projects and everything in `.summer/` (GameSoul.md, memory, cloud state).
- The `summer` binary and every CLI command.
- The npm package name `summer-engine` and the `npx -y summer-engine@latest …` invocations.
- Auth: `~/.summer/` tokens and sign-in state.
- Agent MCP configs — `summer setup` migrates anything that needs touching.

## Aliases: old names keep resolving

Every pre-v3 skill path and name has an alias in `registry/generated/aliases.json` mapping it to the new permanent ID (`skill/<slug>`, `template/<slug>`, …). Anything that references an old path — older docs, saved prompts, other tools — resolves for at least one major release. Removal of alias support requires a changelog entry.

## For contributors

The contribution flow changed: instead of registering a skill in multiple manifests by hand, you add one `library/<kind>/<slug>/` folder and regenerate. See [`DEVELOPMENT.md`](DEVELOPMENT.md#adding-a-library-entry).
