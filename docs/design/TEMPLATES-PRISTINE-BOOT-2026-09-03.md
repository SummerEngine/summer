# Pinned templates on a pristine project: boot verification (2026-09-03)

Read-only verification. No tracked file in the shared worktree was modified; no editor
was launched; `~/.summer` was only read (instances dir empty before and after every run).

## 0. Verdict

- **1 of 17** pinned templates passes `bash tests/autopilot/run.sh` on a project created by
  `summer create` and never opened in an editor: the control `2d-platformer @ ad9d630499c9`
  (exit 0, `errors_seen: []`, both waypoints reached, 3 frames).
- **13 of 17** fail with engine errors (`FAILED: N engine error(s) during the run`, N = 3 .. 1148).
  Two of those are fatal: `3d-fps-simple-animated-npc` and `3d-third-person-controller` never
  load `main.tscn` (`ERROR: Failed loading scene: res://main.tscn.`), so the probe never starts and
  `run.sh` prints `No results.json — the probe never started.`
- **2 of 17** boot with **zero** engine errors but still exit 1 because the autopilot scaffold's
  default `CONFIG` does not fit them: `3d-city-kit` (`player not found at 'Player'`, it is a
  workspace scene) and `3d-fps-old-school` (`waypoints not reached: waypoint_0_reached`, the
  default waypoints are 2D pixel values, the game is 3D metres).
- Every engine error on every failing template belongs to **one class with three faces**: caches the
  editor writes under `.godot/` that a fresh clone never has, (a) `.godot/imported/*`,
  (b) `.godot/uid_cache.bin`, (c) `.godot/global_script_class_cache.cfg`. Section 5 covers why an
  import-first pass in `--summer-verify` would remove all three, and what it would not fix.
- Manifest drift: only 3 of 16 `template.json` versions match `resource.yaml` (`2d-rpg` has no
  `template.json`); `2d-grid-puzzle` is a 3D project labelled 2D; `3d-royale-clash-type`'s
  `project.godot` description describes a different game.

## 5. Would `--summer-verify` importing assets first fix the class?

What the engine does today: the `summer_verify` blocks in `main/main.cpp` (arg parsing ~1912-1934, audio/ceiling ~2545-2553, logger 2605-2607, window 3050-3058, probe injection ~4973-5004) never touch `EditorFileSystem`, importing, or the caches. The verify child is a plain game-mode run of the editor binary; the binary does expose Godot's `--import` ("Starts the editor, waits for any resources to be imported, and then quits", `main.cpp:841`, editor-only availability).

If `--summer-verify` (or `run.sh`) first ran the equivalent of `--import` on the project, i.e. a full `EditorFileSystem` scan plus reimport, that single pass produces all three caches: `.godot/imported/*` (and creates missing `*.import` files with default settings), `.godot/uid_cache.bin` (the scan registers every uid, which also silences the `resource_format_text.cpp:516` WARNING path because `has_id(uid)` becomes true), and `.godot/global_script_class_cache.cfg` (the scan collects `class_name`s). By the classification in section 3 that removes **every** engine error line on all 13 failing templates, including the two fatal `Failed loading scene: res://main.tscn.` cases (third-person: 196 uid + 190 import + 12 class lines; fps-npc: 20 + 6 + 29 + creation of its 6 missing `.import` files). Not verified empirically here: running the headless editor was out of scope (it is an editor launch and it registers `~/.summer/instances/*.json`).

Two caveats on scope: (1) the pass must be the editor scan, not just "import the assets": the uid and class caches come from the scan, and importing alone would still leave every uid WARNING (and thus a failing gate, T-03) and every `class_name` parse error; (2) it fixes only the pristine-project class. It would not change: the scaffold-fit failures (T-04: `player not found`, 2D-pixel waypoints) which would then be the sole reason 16 of 17 still exit 1; genuine template bugs (`%Grenade`, `Case mismatch` on `user://Demo`); the `2d-dungeon-roguelike` visibility issue. The practical alternative the `2d-platformer` fix took (strip uids, ship no imported assets, avoid cross-file `class_name`) does not scale to asset-heavy templates (T-09).

## 6. Caveats

- `errors_seen` counts WARNINGs (T-03); the E/W/S split above is from the `TYPE|` prefix of each line.
- The `%Name` check is a regex over `.gd` files (`%[A-Za-z_][A-Za-z0-9_]*`, single-letter format specifiers excluded); the remaining candidates were resolved by reading the source lines (all `"..." % value` format expressions except `%Grenade`). "Resolved" means some `.tscn` in the project has a node of that name with `unique_name_in_owner = true`, not that the owner relationship is correct.
- "main scene has `Player` child" is a static proxy only; the probe binds `get_tree().current_scene.get_node_or_null("Player")` after 30 physics frames, so scenes that switch at runtime (as `2d-platformer` does) can still bind.
- The verify child ran with a real renderer in an off-screen, no-focus window (`--summer-verify`), which the task rule accepts; `--headless` is explicitly refused by `run.sh` because it cannot capture frames.
- `create` recorded `engine_version: null` because no engine was running; that is `detectEngineVersion()` behaving as documented.
- The toolkit copy includes another agent's uncommitted `src/` edits (listed in section 1); none touch the `create`/templates/autopilot path, and the produced pins/digests match the manifests exactly.
- `~/.summer/mcp.log` has mtime `19:54:10`, before the run loop started (~19:56:05); it belongs to the toolkit MCP server of this session, not to the engine children. Nothing else under `~/.summer` changed (`auth-token`/`user.json` 18:46, `instances/` 19:05 and empty).
