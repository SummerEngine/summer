# Gemini CLI integration

Generated by `scripts/generate-registry` from `library/**/resource.yaml`:

- `registry/generated/gemini-extension.json` -> `gemini-extension.json`
  (extension manifest: MCP server, GEMINI.md context file, settings; version
  stamped from `package.json`). The `skills` array is emitted for parity with
  the other manifests but Gemini has no such field — it discovers extension
  skills from `<extension>/skills/<name>/SKILL.md` and ignores unknown keys.

`summer setup gemini` writes `~/.gemini/extensions/summer-engine/`:

- `gemini-extension.json` — the generated manifest above with install-time
  overrides: `name` becomes `summer-engine` (Gemini requires the manifest name
  to match the extension directory), `mcpServers.summer-engine` becomes the
  standard launcher (`npx -y summer-engine@latest mcp`, `cmd.exe /c` wrapped on
  Windows) because `${extensionPath}` holds no npm package, `skills` and the
  `_generated` banner are dropped.
- `GEMINI.md` and `AGENTS.md` (the context file and the file it imports).
- `skills/<slug>/SKILL.md` for every library skill (via
  `skills install --all --agent gemini`); Gemini extensions are user-scoped, so
  `--scope project` falls back to user with a warning.

Never edit the destination file by hand — edit `library/` resources or
`scripts/generate-registry/manifests.ts`, then run
`npm run generate:registry`. CI `--check` fails on any drift.
